## What this project is

Python 3 remote-control server for **SPE Expert** HF amplifiers (1.3K-FA, 1.5K-FA, 2K-FA). Runs on a Raspberry Pi, opens the USB-serial port to the amp, and serves a single WebSocket on `:8888` that fans out to:

- the bundled browser dashboard at `http://pi:8888`
- Node-RED on the Pi
- the MacExpert companion app

The Python server is the **only** process that ever opens `/dev/ttyUSB0`. Every other client speaks WebSocket. This is the whole reason the project exists — Node-RED used to hold the serial port directly and locked everyone else out.

## Layout

```
server.py              main async server (serial reader thread + ws broadcast)
power_spe_on.py        DTR-line power-on helper
config.yaml            serial port, baud, poll intervals, temp unit, log level
spe/                   protocol module (parser, command builder, RCU framing)
spe/__init__.py        __version__ — bump at every release (update check compares it)
spe/update_check.py    GitHub new-release check (24 h after a success, 1 h after a failure) → /api/update → banner
tests/                 no-hardware tests, run each with python3 tests/<file>.py
web/                   browser dashboard (static HTML/JS/CSS, canvas gauges)
systemd/               unit file for spe-remote.service
install-service.sh     installs + enables the systemd unit
uninstall-service.sh   reverse of above
run.sh                 dev launcher
setup.sh               first-time venv + deps install
docs/                  protocol notes, Node-RED sample flow
```

5. **Sweep tuning: auto-STBY, band verification, OPERATE restore (2026-09-02, `a1c1252` — vu2cpl-shack TODO #44)** — the band sweep used to trust the operator on two fronts: the amp had to already be in STBY (preflight FAILed otherwise) and the requested band was swept blindly even if the radio — and therefore the antenna on the amp — was on a different band. `TuneOrchestrator` now: (1) **drops the amp to STBY itself** at the start of `tune_single`/`tune_band` — CMD_OPERATE is a *toggle*, so the switch is verified against the CSV `op_status` (new `OPER_SWITCH_TIMEOUT` 4 s) rather than assumed, and the prior mode is remembered; (2) **verifies the sweep band against the radio** before anything moves — the operator slice's freq (waiting up to `SLICE_STATE_TIMEOUT` 2 s for the post-connect `sub slice all` events) is mapped to its ham band via the new `spe_band_table.band_for_freq()`, a mismatch FAILs the sweep (wrong-antenna protection), `tune_band:auto` (also `current`/empty) sweeps the radio's current band, and an underivable radio band trusts an explicit request with a note; (3) **restores OPERATE at the end iff it was on at the start**, on every exit path (success/FAIL/ABORT) — the restore runs in the finally after carrier-off + VFO restore and ignores the stop flag so an aborted sweep still hands the amp back. The per-cycle STBY preflight stays as a safety net against mid-sweep front-panel flips; antenna selection remains the operator's job. Verified with a fake-serial/fake-flex harness (41 checks incl. stop-mid-sweep restore and mismatch refusal); **verified on-air 2026-09-02** (same evening): a full 40m sweep ran 12/12 sub-bands in 47 s — STBY confirmed via op_status 0.5 s after the toggle, before any TUNE keycode; every cycle LED_ON → CARRIER_ON 10 W → LED_OFF (ATU 1.4–2.1 s per sub-band); VFO restored (7.100 LSB) and OPERATE back 0.5 s after SWEEP_DONE. 6. **AetherSDR v26.8.2 SPE support noted; ser2net shim deferred (2026-08-24, `37b074a`)** — AetherSDR v26.8.2 (`aethersdr/AetherSDR#4531`, @opalito) shipped SPE Expert support via **direct serial** or **ser2net TCP** (raw or telnet, RFC 2217 for the DTR power-ON pulse) with its own 100 ms status poller. That protocol shape is incompatible with our WebSocket + JSON server, and even a byte-proxy shim on top of spe-remote runs into two problems: (a) SPE responses aren't tagged, so two 100 ms pollers on the same port will scramble replies — a shim would need to fan out the bytes we're already polling and swallow AetherSDR's polls, and (b) writes need a mutex around the shared `SerialHandler` plus RFC 2217 COM-PORT-CONTROL wiring into `PowerController`'s DTR sequence. Parked under "Open threads" pending a **ser2net-only trial** (stop `spe-remote.service`, run `ser2net` on the FTDI, point AetherSDR at it) that decides whether AetherSDR's SPE is worth building the shim for. Also two operational things surfaced during triage: (i) if the front-end shows "WS connected" but controls do nothing, check `journalctl -u spe-remote.service -n 50 -l` for repeated `Serial write failed: write failed: [Errno 5] Input/output error` — that's a stale FTDI file descriptor after a USB-bus event (cable jiggle, amp power-cycle, USB hub glitch), fix is `sudo systemctl restart spe-remote.service`; distinct failure mode from the FTDI-wedge bug fixed in `3f69277` (self-inflicted second-pyserial-handle); (ii) new "Power control — how the button actually works" reference section further down documents the full WS → `PowerController` → `SerialHandler._port` call chain for both ON (DTR/RTS ioctl sequence) and OFF (serial command `0x0A`).
7. **Flex: on-demand connect at Sweep-menu open, disconnect when the cycle ends (2026-06-27, PR #3 by VU3ESV/LB9KJ, `8a02c11`)** — spe-remote used to open the SmartSDR TCP session at startup and hold it for the life of the process, so the radio was marked "in use" by spe-remote whenever the daemon was up, and the radio had to be powered at startup (or spe-remote restarted after a radio power-cycle). New `spe/flex_controller.py` `FlexController` owns at most one `FlexConnection`, opened/closed on demand under an `asyncio.Lock`; `connect()` resolves the host lazily (`flex.host`, else UDP discovery) so the radio may be off at startup and still be found later; both `connect()`/`disconnect()` are idempotent and never raise. `TuneOrchestrator` acquires the connection at the start of `tune_single`/`tune_band` and releases it in the `finally` — even on failure/abort — with a sweep holding one connection across all sub-bands. New WS commands `flex_connect` / `flex_disconnect` let the web dashboard pre-warm on Sweep-panel open and drop on idle close (`flex_disconnect` is ignored mid-tune; both are no-ops when `flex.enabled: false`). State transitions broadcast as new `tune_event` phases `FLEX_CONNECTING` / `FLEX_CONNECTED` / `FLEX_DISCONNECTED` / `FLEX_ERROR`. **Backward compatible** — older clients (MacExpert, Node-RED, Vue) that only send `tune_band`/`tune_stop` still work via the lazy connect-at-tune-start path and inherit disconnect-when-done for free. Tested with a fake `FlexConnection` (idempotent connect/disconnect/reconnect, correct phase sequence, tune failure path still releases the radio) — not yet run against a live radio at merge time.
8. **SPE power meter: server-side AVG (EMA) + PEAK (peak-hold) (2026-06-27)** — `AmplifierState` gains two `p_out`-derived float fields: `p_out_avg` (EMA, α=0.15, ~1 s settle at the 25 Hz TX poll) and `p_out_peak` (peak-hold — pins the highest sample for 2.5 s then decays toward the live reading at a constant 600 W/s). Both computed in `SerialHandler._consume_csv_frame` and reset across an op/tx transition so a fresh TX isn't dragged by the prior idle reading; raw `p_out` is untouched, so existing consumers are unaffected. Lets clients offer RAW / AVG / PEAK meter modes without each re-deriving the ballistics — the `vu2cpl-shack` dashboards (D1 `/ui` + Vue `/shack`) consume them through a pill toggle. **`p_out_peak` is a *sampled* peak, not true envelope PEP** (25 Hz → ~40 ms blind spots); the field doc-comment + README say so. Origin: a contributed feature package (adersh fork) whose peak-decay math compounded `decay_s` every frame — an accelerating, sample-rate-dependent fall (1500→0 in ~0.46 s) instead of the documented constant 600 W/s. The version landed here uses a per-frame `dt`-scaled decrement (verified 2.50 s for 1500→0, frame-rate independent). If that package is ever re-imported, re-apply this fix.

10. **Interactive configurator + service-update flow (2026-06-20, PR #1 by VU3ESV/LB9KJ)** — first-time install on a Pi used to mean hand-editing `config.yaml` to find the right `/dev/serial/by-id/...` path, and re-installs could clobber the saved port and Flex IP. ## Architecture invariants — don't break these

- **Only one process opens the serial port.** If you ever find yourself adding a second `serial.Serial(...)` call, stop. The power-control path was the trap that caused `3f69277`.
- **Threaded reader + async writer.** Blocking reads run on a thread because `serial_asyncio` was crashing on USB-serial poll glitches. Don't "modernize" this back to pure asyncio without testing on a real Pi + FTDI.
- **Mixed-client broadcast on the same WS.** Text JSON for browsers, binary RCU frames for MacExpert. Same socket, dispatched by message type.
- **Python 3.9 floor.** No `match` statements, no `X | Y` type unions in runtime code. Bookworm Pi is the deployment target.
- **No saturating the amp.** TX-poll interval and RCU tick rate were tuned by trial; bumping them up will wedge the amp's serial buffer again.

## Power control — how the button actually works

Power ON and OFF use **different mechanisms** because the SPE protocol has no "power on" command — only "off". Documenting the full call path here so future-Manoj doesn't have to re-derive it from the code.

**Power ON** (hardware DTR/RTS toggle):

```
browser button
  → WS text frame "power_on"
  → spe/websocket_handler.py  _handle_power("power_on")
  → spe/power_control.py      PowerController.power_on()
  → run_in_executor → _power_on_sync()
  → ioctls on SerialHandler._port (the already-open FTDI handle):
      DTR=1 → DTR=0 → RTS=1 → sleep 1s → DTR=1 → RTS=0
  → amp boots in 3–4.5 s
  → server replies with {"power_result":"power_on","status":"ok"}
```

**Power OFF** (serial command, not hardware lines):

```
browser button
  → WS text frame "power_off"
  → _handle_power("power_off")
  → PowerController.power_off()
  → SerialHandler.send_command("power_off")
  → command byte 0x0A goes out on the same serial port (SWITCH OFF, per
    SPE Application Programmer's Guide Rev 1.1)
```

**Why `_power_on_sync` reaches into `SerialHandler._port` directly** instead of opening its own `serial.Serial(...)`: pyserial's `open()` reconfigures termios and toggles DTR/RTS as a side effect. The original code did open a second handle (mirroring OH2GEK's standalone `power_spe_on.py`) and it wedged the FTDI driver on the second power action in a session. The fix in commit `3f69277` was to assign `.dtr` / `.rts` directly on the existing fd — those are pure ioctls, no termios churn, no second handle. **If you ever find yourself "cleaning this up" by opening a fresh Serial(), re-read that commit first.**

**Side effects of the DTR sequence:**

- While DTR is held high, the amp's front-panel power switch is overridden. The front panel shows `POWER SWITCH HELD BY REMOTE`.
- The hardware lines work whether the amp's CPU is alive or not — that's the whole point. The 2026-05-15 client-consolidation work (Recent work item 14) was triggered by a Node-RED flow that wrongly assumed the WS path couldn't wake a powered-off amp because the *data* link was dead. The data link is irrelevant; DTR is a separate wire.

**Standalone `power_spe_on.py` at the repo root** is the OH2GEK original. Kept as a fallback for the case where `spe-remote.service` itself is down. **Do not invoke it while the service is running** — that's the second-pyserial-handle trap the architecture-invariant section warns about.

## Config (`config.yaml`)

- `serial.port` — uses the stable `/dev/serial/by-id/...` path, not `/dev/ttyUSB0`. Don't switch back; ttyUSB numbering changes across reboots.
- `polling.tx_interval` 0.2s, `idle_interval` 1.0s, `heartbeat` 15s — leave these alone unless you have a scope on the wire. The Pi runs locally-tweaked 0.1 / 0.4 values that are not in the default file.
- `polling.amp_alive_threshold` 3s — applies to the most recent of CSV state OR RCU display frame (see item 15 in Recent work). RCU OFF→ON ticks at 1.5s, so 3s is a generous margin while still flipping `serial:"down"` within ~3s of amp power-off (FTDI link survives, but no more RCU frames come back).
- `amp.temperature_unit` C or F — must match the SPE front-panel setting.
- `logging.level` INFO by default; DEBUG is loud (every serial write).
- `updates.check` true by default (section may be absent) — the GitHub new-release check (24 h after a successful check, 1 h after a failed one; never on a `dev` version). Not in the committed `config.yaml` on purpose (see Recent work 1).

## Deployment

systemd unit `spe-remote.service` runs the server as a daemon. `install-service.sh` is the supported install path; the README tells users to clone the repo, run `setup.sh`, then `install-service.sh`. Service logs go to journald. Documented update path (README "7. Updating", also shown in the new-release banner): `git pull --ff-only && sudo systemctl restart spe-remote` in the clone (Manoj's routine, since 2026-10-09); `./setup.sh` only when a release changes `requirements.txt`, `sudo ./install-service.sh` only when it changes the systemd unit — say so in that release's notes.

### Release checklist

1. In the release commit, bump `__version__` in `spe/__init__.py` to the new tag's number (tag `v3.1.0` ⇒ `"3.1.0"`). The update check compares this with the latest release tag — forget it and every install keeps announcing the release it already runs. Never leave "dev" in a released `__version__` — a dev version does not check at all.
2. Bump the `Version` row in `docs/generate_guide.py` and regenerate `docs/SPE_Remote_Control_User_Guide.pdf` in the same commit (lesson from v3.0.0).
3. Tag `vX.Y.Z`, publish the GitHub release (it must be a full release, not a pre-release — `/releases/latest` skips pre-releases and drafts).
